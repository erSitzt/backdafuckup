# Broadcom Locks the Data Path, Not the APIs

**No, not everything is publicly available any more.** The vSphere control plane that a backup product needs is still public or sits behind a free Broadcom account: the snapshot, Changed Block Tracking (CBT) and quiescing calls, their API reference, the WSDL, and Apache-2.0 reference bindings. A C#/.NET 10 client can be built without any partner status. The data path is different. Since about **25 August 2026 Broadcom has withdrawn the Virtual Disk Development Kit (VDDK) from public download**. Broadcom says VDDK is now available only "through select TAP partners" for backup and recovery, and bundling it in a product needs a separately signed redistribution agreement ([TechTarget](https://www.techtarget.com/it-infrastructure/news/366648768/Broadcom-confirms-change-in-VMware-migration-tool-access); [ShapeBlue](https://www.shapeblue.com/broadcom-vddk-download-vmware-to-kvm/)). Joining the Technology Alliance Program (TAP) is free. Getting VDDK through it is at Broadcom's discretion, the criteria are not published, and the SDK licence behind it can be ended "for any reason at any time" ([Broadcom SDK License Agreement](https://docs.broadcom.com/doc/vmware-software-development-kit-license-agreement)). Customers need a paid vSphere licence, because free ESXi blocks the backup APIs. A properly licensed development lab needs TAP Not-for-Resale (NFR) licences or roughly **$800–2,160 a year** in subscriptions. VDDK-free alternatives now have working precedents, and the most complete one comes from Vates, the company behind XCP-ng. Phase 2 therefore does not have to wait for Broadcom. The safest alternative is HotAdd built on public `ReconfigVM_Task` calls, which carries low legal risk. A clean-room NFC client is also workable, but it needs a lawyer's review first. Hyper-V needs nothing except engineering time.

> **Legal caveat:** every licensing, contract and copyright point in this report is non-lawyer research and not legal advice. Have counsel review it, in both the EU/Germany and the US, before acting on it.

## One partner-only library gates an otherwise open stack

## Snapshot and CBT APIs stay public, but .NET gets no SDK

VADP is not a separate API. It is a name for a group of documented capabilities. The vim25 methods `CreateSnapshot_Task`, `ReconfigVM_Task` with `changeTrackingEnabled`, `QueryChangedDiskAreas` and `RemoveSnapshot_Task` handle orchestration. VMware Tools' VSS component handles application-consistent quiescing. VDDK moves the data. Broadcom still publishes the backup-design chapters and the **Web Services API reference up to 9.1.1 without login** ([Broadcom: Backing Up Virtual Disks](https://developer.broadcom.com/xapis/virtual-disk-api/latest/vddkBkupVadp.9.1.html); [Broadcom: vim.VirtualMachine](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.VirtualMachine.html)). The constraints are technical, not contractual. CBT needs virtual hardware version 7 or later. Enabling it on a running VM forces a stun/unstun cycle. `QueryChangedDiskAreas` needs the `VirtualMachine.Provisioning.DiskRandomRead` privilege. Quiescing and memory snapshots cannot be combined ([Broadcom: Low Level Backup Procedures](https://developer.broadcom.com/xapis/virtual-disk-api/latest/vddkBkupVadp.9.3.html)).

The customer's host licence alone decides whether these calls work. Broadcom's free-ESXi KB contrasts the paid licence, which includes "API-based backup", with the free one, which has "No access to vMotion, DRS, HA, VADP-based backups". On free ESXi, APIs "may only provide read-only information", and the free version tops out at **2 physical CPUs and 8 vCPUs per VM** ([Broadcom KB 399823](https://knowledge.broadcom.com/external/article/399823/free-version-of-vmware-esxi.html)). Veeam v13 likewise does not support free ESXi ([Veeam Help Center](https://helpcenter.veeam.com/docs/vbr/userguide/platform_support_vm.html)). Among paid editions, no current Broadcom document separates VADP, CBT or snapshots by edition. The bigger issue is how the lineup is shrinking. **vSphere Standard and Enterprise Plus stop at 8.0 Update 3, and vSphere 9.1 is sold only inside VVF and VCF** ([Broadcom Product Line Comparison](https://www.vmware.com/docs/vmw-datasheet-vsphere-product-line-comparison)). Essentials Plus is gone ([Thomas-Krenn](https://www.thomas-krenn.com/en/wiki/VMware_license_model_by_Broadcom)). VVF has been withdrawn in "some EMEA countries" ([The Register](https://www.theregister.com/2025/12/11/vmware_kills_vsphere_foundation_parts_emea/)). vSphere 8 general support ends on **11 October 2027** ([Eurokommerz](https://eurokommerz.at/blog/vsphere-standard-and-vvf-end-of-sale/)). By the time Phase 2 ships, most paying customers will be on 9.x.

For .NET, Broadcom offers **no SDK at all**. The 8.0 release notes say ".NET SDK discontinued. C# sample programs in the SDK have been deleted" and tell developers to "generate .NET bindings using WSDLs" ([vSphere Web Services SDK 8.0 release notes](https://techdocs.broadcom.com/us/en/vmware-cis/vsphere/vsphere-sdks-tools/8-0/release-notes/vsphere-management-sdk/vsphere-web-services-sdk-80-release-notes.html)). The .NET Automation SDK was archived in December 2021 ([GitHub](https://github.com/vmware/vsphere-automation-sdk-.net)). Generating a client from `vimService.wsdl` with dotnet-svcutil works, but the result is very large. In a 2018 test it produced about **105 MB of generated source**, a single call allocated 922 MB, and XmlSerializer was mandatory ([dotnet/wcf #3002](https://github.com/dotnet/wcf/issues/3002)). VI/JSON is a cleaner alternative. It mirrors the whole vim25 model over HTTP/JSON with an OpenAPI 3.0 description, but it needs vCenter 8.0 U1 or later and does not work on standalone ESXi ([Broadcom VI/JSON reference](https://developer.broadcom.com/xapis/virtual-infrastructure-json-api/latest); [William Lam](https://williamlam.com/2023/11/is-there-a-vsphere-rest-api-for.html)). The Automation REST API cannot take snapshots, so the vim25 model is still required. The only NuGet wrappers are stale: VimClient 7.0.0 (2022) and NetVimClient 6.7.0 (2019) ([NuGet](https://www.nuget.org/packages?q=vim25)). Broadcom's Go and Python bindings, govmomi and pyVmomi 9.1.1.0, are Apache-2.0 and legally usable as references ([govmomi](https://github.com/vmware/govmomi); [PyPI pyvmomi](https://pypi.org/project/pyvmomi/)).

The SDK licence explicitly allows commercial "Developer Software". It permits redistribution only of code that Broadcom marks as "distributable". The link to that list now redirects to a generic community page. The licence caps Broadcom's liability at **$1,000**, requires you to indemnify Broadcom, and lets either side terminate at will ([Broadcom SDK License Agreement](https://docs.broadcom.com/doc/vmware-software-development-kit-license-agreement)). For that reason PowerCLI's bundled `VimService.dll` should not be shipped ([PowerShell Gallery VMware.Vim](https://www.powershellgallery.com/packages/VMware.Vim)). Stubs you generate yourself are the lower-risk choice. VMware's 2013 SDK FAQ said "the stubs source and the compiled stubs can also be distributed" ([OpenStack mailing list](https://lists.openstack.org/pipermail/openstack/2013-August/000555.html)). Broadcom has not confirmed this since (non-lawyer reading).

## VDDK became partner-only around 25 August 2026

Until mid-2026 anyone with a free developer account could download VDDK. On about 25 August the developer-portal pages began returning 404, with no announcement ([ShapeBlue](https://www.shapeblue.com/broadcom-vddk-download-vmware-to-kvm/)). Broadcom later told the press that "the VDDK is not a customer entitlement", that its "approved use case ... has always been for backup and recovery", and that access "is still available through select TAP partners" ([TechTarget](https://www.techtarget.com/it-infrastructure/news/366648768/Broadcom-confirms-change-in-VMware-migration-tool-access); [The Register](https://www.theregister.com/virtualization/2026/09/10/vmware-defends-ending-downloads-of-sdk-that-helps-vm-backups-or-migrations-to-rivals/5295421)). Network World reports that VDDK is still available to "larger Broadcom software partners" and that Internet Archive copies were removed ([Network World](https://www.networkworld.com/article/4221279/broadcom-hampers-vmware-migration-by-blocking-downloads-of-key-sdk.html)). Broadcom also says migration is "not a licensed use" ([Techzine](https://www.techzine.eu/news/devops/144228/vmware-restricts-vddk-for-migrations/)). Some reports say entitled customers can still find VDDK on the support portal ([It's FOSS](https://itsfoss.com/news/broadcom-removes-vmware-vddk-downloads/)). That conflicts with Broadcom's on-record statement, and it would not help a vendor anyway.

Getting VDDK and shipping it are separate permissions. The default SDK licence grants only "a reasonable number of copies ... for your own internal use" and forbids distributing "any part of the Software" except designated code ([Broadcom SDK License Agreement](https://docs.broadcom.com/doc/vmware-software-development-kit-license-agreement)). Broadcom's VDDK guide says redistribution requires TAP "at Select level or above" and a signed redistribution agreement requested through an alliance manager ([Broadcom VDDK intro](https://developer.broadcom.com/xapis/virtual-disk-api/latest/vddkIntro.3.5.html)). The 8.0 guide reportedly said "Standard level" instead, and the current tier structure is unclear. That agreement is how Commvault ships several certified VDDK versions inside its installer ([Commvault docs](https://documentation.commvault.com/11.42/commcell-console/vddk_support_for_virtual_server_agent_with_vmware_01.html)). Open-source projects never had it, so nbdkit always made users "download yourself" ([nbdkit-vddk-plugin](https://libguestfs.org/nbdkit-vddk-plugin.1.html)). Under the new policy customers can no longer download VDDK themselves either. For a new vendor, **a redistribution agreement is now the only VDDK route**. Its text, fees and audit terms are not public. The 8.x/9.x programming guides and the 9.1 release notes now return 404 as well, so only the 6.0-era guide remains public.

On the technical side, VDDK is a native C library. The current lines are 8.0.3 (June 2024), 9.0.x (June and September 2025) and 9.1, which pairs with vSphere 9.1 from May 2026. It is built **only for x86-64 Linux and Windows**. The tested proxy operating systems for 9.x are Windows Server 2022/2025, RHEL 9, SLES, Oracle Linux and Photon. Ubuntu is not on the list ([VDDK 9.1 release notes, snippet](https://techdocs.broadcom.com/us/en/vmware-cis/vsphere/vsphere-sdks-tools/9-1/release-notes/virtual-disk-development-kit/virtual-disk-development-kit-91-release-notes.html)). Commvault notes that one machine can run only one active VDDK version ([Commvault docs](https://documentation.commvault.com/11.42/commcell-console/vddk_support_for_virtual_server_agent_with_vmware_01.html)). That points to one worker process per VDDK version. No maintained .NET wrapper exists ([VMware communities](https://communities.vmware.com/t5/Virtual-Disk-Development-Kit/VDDK-NET-wrapper/m-p/2067613)), so a .NET 10 product would write its own `[LibraryImport]` layer.

### Every transport mode sits behind the same gate

VDDK offers four network and proxy transports, tried by default in the order **san:hotadd:nbdssl:nbd** ([Broadcom Advanced Transport APIs](https://developer.broadcom.com/xapis/virtual-disk-api/latest/vddkFunctions.6.11.html)). NBD and NBDSSL use the NFC protocol over **TCP 902** to each ESXi host, with 443 for the API. They work from any proxy, and NBDSSL is mandatory for encrypted VMs ([nbdkit-vddk-plugin](https://libguestfs.org/nbdkit-vddk-plugin.1.html); [VDDK 8.0.2 release notes](https://docs.vmware.com/en/VMware-vSphere/8.0/rn/vddk-802-release-notes.html)). For HotAdd, the proxy "must be a virtual machine" that can see the source datastore, and it works only with SCSI disks. For SAN, the proxy "must be a physical machine" with raw LUN access, and SAN does not support vSAN or vVols ([Broadcom Transport Methods](https://developer.broadcom.com/xapis/virtual-disk-api/latest/vddkDataStruct.5.5.html)). VDDK 8.0.3 added NVMe-oF SAN on Linux, and 9.1 lifts the rule that NBD mode needs a direct connection to the ESX host. Every one of these modes comes with VDDK, so all of them are partner-only. Anything equivalent outside VDDK has to be built from public APIs or a clean-room protocol client.

## TAP costs nothing to join, but approval is the bottleneck

Broadcom kept the VMware Technology Alliance Program for independent software vendors, and it is distinct from the **invitation-only Broadcom Advantage program** for resellers ([The Register](https://www.theregister.com/2024/01/10/broadcom_ends_vmware_partner_program/)). The TAP FAQ states: "There is no fee associated with the VMware TAP membership". You register at tap.broadcom.com and the TAP Support Team reviews the application. Certification and integration programs are "generally free" but need a vetting questionnaire. Technical support through the Wolken desk opens only after onboarding into a program, and Compatibility Guide listings cost nothing ([TAP Help/FAQ](https://tap.broadcom.com/help)). Broadcom's NFR KB sends vendors "developing an adjacent offering like backup" to TAP and gives NFR quantities based on alignment with Broadcom's strategy ([Broadcom KB 373980](https://knowledge.broadcom.com/external/article/373980/not-for-resale-vmware-license-informatio.html)). Certification looks optional. VMware's long-standing position is that backup software is "partner supported" and that joint issues go through TSANet ([VMware KB 2007904](https://kb.vmware.com/s/article/2007904), older wording). VAIO I/O filters are the exception. They have always required vetting, certification and a signed certificate ([VMware Storage blog](https://blogs.vmware.com/storage/2015/02/05/vsphere-apis-io-filtering/)).

The open question is the word "select". No source says what makes a TAP member eligible for VDDK, how long approval takes, or whether a pre-revenue vendor qualifies ([ServNet UK](https://www.servnetuk.com/news/broadcom-vmware-sdk-download-block-2026)). No first-hand account from a small backup vendor applying after August 2026 turned up. The TAP Membership Agreement is behind a login, so it is unknown whether it contains confidentiality or reverse-engineering clauses. The incumbents (Veeam, Commvault, Veritas, Rubrik) appear to have kept access ([Integration Plumbers](https://www.integrationplumbers.io/resources/vddk-independent-migration-stack)). A newcomer faces an unclear gate held by a vendor whose analysts warn of growing "vendor lock-in" ([TechTarget](https://www.techtarget.com/it-infrastructure/news/366648768/Broadcom-confirms-change-in-VMware-migration-tool-access)).

## A properly licensed lab needs NFRs or about $2,000 a year

Evaluation mode is built in. It gives **60 days on vSphere 8**, with "features equal to a vSphere Enterprise Plus license", and **90 days on VCF/VVF 9**, so CBT, snapshots and VADP all work during the trial ([vSphere 8 docs](https://docs.vmware.com/en/VMware-vSphere/8.0/vsphere-vcenter-esxi-management/GUID-82C20FE0-306E-448D-A181-C4A822E664A8.html); [VCF 9.0 licensing blog](https://blogs.vmware.com/cloud-foundation/2025/06/24/licensing-in-vmware-cloud-foundation-9-0/)). The problem is the binaries. Community reports say trial downloads are offered only to active customers ([Broadcom Community](https://community.broadcom.com/vmware-cloud-foundation/question/esxi-download-as-tiral-edition-of-60-days)). Even William Lam notes that VCF 9 download tokens need a support entitlement ([williamlam.com](https://williamlam.com/2025/07/how-to-deploy-vvf-vcf-9-0-using-vmug-advantage-vcp-vcf-certification-entitlement.html)). Reinstalling over and over to reset the clock conflicts with the "for the period limited by the License Key" evaluation terms. That makes it a weak legal basis for long-lived CI.

The cheaper-looking options do not fit. Free ESXi downloads with a free account, but its read-only API makes it useful only as a physical host for nested labs or for negative-path tests ([Broadcom KB 399823](https://knowledge.broadcom.com/external/article/399823/vmware-esxi-80-update-3e-now-available-a.html)). VMUG Advantage costs $210 a year, gives VCF licences only to members who pass VCP-VCF, and is for personal, non-commercial use ([VMUG Advantage](https://vmug.com/advantage); [VMware VCF blog](https://blogs.vmware.com/cloud-foundation/2025/04/14/free-home-lab-licenses-for-vmware-certified-professionals/)). Hands-on Labs are guided training sessions that need a corporate email ([vInfrastructure](https://vinfrastructure.it/2025/09/01/)). That leaves **TAP NFRs**, which come "with support" and are meant for interoperability development, testing and certification ([tap.broadcom.com](https://tap.broadcom.com/)), or a paid subscription. Reported list prices are about **$50, $135 and $350 per core per year** for VVS, VVF and VCF, with a 16-core minimum per CPU ([AceMQ](https://acemq.com/blogs/vmware-cloud-foundation-vs-vsphere-foundation/)). One 16-core host therefore costs about $800 a year on Standard, which stops at 8.0 U3 and has disputed availability, or **$2,160 a year on VVF**, which covers 9.x. A 72-core order minimum would raise these figures to about $3,600 and $9,720. Sources disagree on whether that minimum still applies ([The Register](https://www.theregister.com/2025/03/28/arrow_vmware_licensing_change/); [Stackscale](https://www.stackscale.com/blog/vmware-licensing-2026/)).

Nesting reduces the hardware needed but not the licences. Lam's nested ESX 9.1 appliance and VCF/VVF 9.1 lab scripts are the standard way to build a nested lab, and they support NBD/NBDSSL and HotAdd testing ([williamlam.com](https://williamlam.com/2026/05/vcf-9-1-automated-vmware-cloud-foundation-vcf-vmware-vsphere-foundation-vvf-nested-lab-deployment.html)). Each nested ESXi host still needs its own licence. For CI, govmomi's `vcsim` simulates snapshot create, revert and remove, the CBT reconfigure call and HttpNfcLease exports. It does **not** implement `QueryChangedDiskAreas` ([govmomi simulator](https://github.com/vmware/govmomi/blob/main/simulator/virtual_machine.go)), so the CBT logic needs a mock or a real host.

## VDDK-free data paths work, and HotAdd carries the least risk

The August cut-off triggered a burst of open-source work. **Xen Orchestra removed VDDK entirely on 25 September 2026** and now reads disks through `vectura`, its own NFC client licensed AGPL-3.0, with CBT doing extent discovery ([XO PR #10421](https://github.com/vatesfr/xen-orchestra/pull/10421); [XO CHANGELOG](https://github.com/vatesfr/xen-orchestra/blob/master/CHANGELOG.md)). nbdkit deprecated its VDDK plugin on 17 October ([nbdkit commit](https://gitlab.com/nbdkit/nbdkit/-/commit/b8284518411a)). XO is the closest precedent for this product. It is a commercial vendor in the XCP-ng ecosystem running a full VDDK-free path with CBT.

| Path | Full backup (running VM) | CBT incremental | Restore | Throughput | Legal risk |
|---|---|---|---|---|---|
| HotAdd via `ReconfigVM_Task` (own code) | Yes | Yes | Yes, block-level with a persistent attach | Highest | **Low** |
| `ExportSnapshot` / `ImportVApp` (HttpNfcLease) | Yes | No (sequential stream) | Whole VM only | Single stream | **Lowest** |
| Datastore HTTP `/folder` with Range | Probably (frozen base under a snapshot) | Possible in principle | Whole disk only (PUT) | About 70–130 MB/s, 4 connections | **Lowest** |
| Clean-room C# NFC client | Yes | Yes | Only if you build writes | Medium | **Medium** |
| Apache-2.0 OpenVDDK drop-in | Yes | Yes (reads) | No (read-only) | Claimed above VDDK | **Medium** |

**HotAdd without VDDK** relies only on public calls. Snapshot the source VM. Attach the frozen base VMDK to a proxy VM with `ReconfigVM_Task`. Read the CBT extents from the resulting block device, then detach. XO's code attaches disks in `independent_nonpersistent` mode, because "vSphere has no read-only disk mode". It also confirms that local, shared and vSAN datastores all work whenever the proxy's host mounts them ([XO esxi.mjs](https://github.com/vatesfr/xen-orchestra/blob/master/@xen-orchestra/vmware-explorer/esxi.mjs)). The constraints VDDK documents still apply: the proxy must be a VM and only SCSI disks work. Most of the hard work is robustness: crash journals, cleanup of disks left attached, and stopping the proxy OS from auto-mounting what it sees. VDDK blocks vMotion during a backup with `DisableMethods`, which is outside the public WSDL. Leaving that call out keeps the design entirely within public APIs ([OpenVDDK PROVENANCE](https://github.com/openvddk/openvddk/blob/main/PROVENANCE.md)).

**The public HTTP paths are legally the safest but weak technically.** `ExportSnapshot` has been in the API since 5.5 and lists no power-state fault, so it can do full backups of running VMs. It produces a sequential stream-optimised VMDK, and while the lease is held it blocks state changes on the VM ([Broadcom: VirtualMachineSnapshot](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.vm.Snapshot.html); [Broadcom: HttpNfcLease](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.HttpNfcLease.html)). Proxmox's importer uses `/folder` with Range reads. It caps itself at four connections because ESXi blocks heavy clients for about 30 seconds, and it does not work on vSAN ([Proxmox wiki](https://pve.proxmox.com/wiki/Migrate_to_Proxmox_VE)). Vates measured that `/folder` takes its own lock on the files it serves, which can collide with other backup tools ([vectura limits](https://github.com/vatesfr/xen-orchestra/blob/master/@xen-orchestra/vmware-explorer/vectura/docs/reference/host-requirements-and-limits.md)).

**NFC is the network-mode equivalent of NBD, and it is undocumented.** It has no public wire specification, and the ticket call it needs (`NfcGetVmFiles` via `RetrieveInternalContent`) is an internal API. The three new implementations rest on different provenance. vectura says it was "written from public sources only", meaning the API reference, KBs and observation of ESXi ([vectura design notes](https://github.com/vatesfr/xen-orchestra/blob/master/@xen-orchestra/vmware-explorer/vectura/docs/explanation/scope-and-design-choices.md)). Cloudbase's OpenVixDiskLib was "reverse-engineered from VDDK 8 NBD traffic", including TLS interception, and its licence is unclear ([cloudbase/OpenVixDiskLib](https://github.com/cloudbase/OpenVixDiskLib)). The Apache-2.0 OpenVDDK (v0.7.4) is read-only, Linux-only and maintained by one person ([openvddk](https://github.com/openvddk/openvddk)). A GPL "OpenVDDK" made broad claims and has since disappeared from GitHub. None of these has been tested against vSphere 9.x.

**Legal framing (non-lawyer research, not legal advice).** In the EU, Directive 2009/24/EC lets a lawful user "observe, study or test" a program (Art. 5(3)) and decompile it for interoperability under strict conditions (Art. 6). Art. 8 makes contract terms that override these rights "null and void" ([Art. 5](https://www.legislation.gov.uk/eudr/2009/24/article/5); [Art. 8](https://www.legislation.gov.uk/eudr/2009/24/article/8)). Germany implements these articles in §§69d(3), 69e and 69g(2) UrhG. The CJEU's *SAS Institute v WPL* ruling confirms that functionality is not protected by copyright ([Fieldfisher](https://www.fieldfisher.com/en/insights/sas-institute-inc-v-world-programming-limited)). Broadcom's own SDK licence exempts mandatory law that implements the EC Software Directive. Two limits remain. The Trade Secrets Directive accepts contractual limits on reverse engineering ([Carpmaels](https://www.carpmaels.com/eu-trade-secrets-directive/)). In the US, *Bowers v. Baystate* upheld a shrink-wrap clause banning reverse engineering ([FindLaw](https://caselaw.findlaw.com/court/us-federal-circuit/1202776.html)). Observing ESXi's own NFC server carries the least risk. Observing VDDK traffic carries more, and decompiling VDDK should be ruled out. **Signing TAP or VDDK agreements first could contractually close off the cleaner route.**

## Hyper-V asks for engineering time, not permission

On Hyper-V, everything is published. Microsoft has a developer-facing "Hyper-V Backup Approaches" page that covers WMI v2 checkpoints, RCT reference points and three data-read methods ([MS Learn](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/backup-approaches)). The change-query call, `QueryChangesVirtualDisk`, is a plain Win32 export from virtdisk.dll ([MS Learn](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-querychangesvirtualdisk)). VSS headers and samples ship in the free Windows SDK, and Microsoft.Management.Infrastructure is MIT-licensed on NuGet ([NuGet](https://www.nuget.org/packages/Microsoft.Management.Infrastructure)). No certification or logo is required, and the full API can be tested at no cost on Windows 11 Hyper-V, on Hyper-V Server 2019 (supported until January 2029), or on a 180-day Windows Server evaluation ([Microsoft Tech Community](https://techcommunity.microsoft.com/discussions/windowsserverinsiders/hyper-v-server-2022/2652790)). The costs are engineering ones. The only official sample is a 2014 PowerShell module, and virtdisk change queries work only locally, so the data mover has to run on each Windows host ([MicrosoftDocs xhypervbackup](https://github.com/MicrosoftDocs/Virtualization-Documentation/tree/main/hyperv-samples/taylorb-wmi/xhypervbackup)).

## Risks that could derail Phase 2

| Risk | Severity | Mitigation |
|---|---|---|
| Broadcom denies or delays VDDK access for a new, small vendor ("select TAP", criteria unpublished) | High | Build a VDDK-free baseline. Apply to TAP early |
| VDDK access is revoked later. The SDK licence is terminable at will and termination requires destroying all copies | High | Data-mover abstraction plus a VDDK-free fallback |
| Use-case scope: VDDK is licensed for backup and recovery, and Broadcom calls migration "not a licensed use". Restoring vSphere backups onto XCP-ng is this product's natural cross-sell | Medium–High | Ask Broadcom in writing before signing. Keep cross-hypervisor restore off VDDK |
| Exposure from a clean-room NFC client: undocumented protocol, internal API, US contract law, and conflicts with any TAP terms you sign | Medium | Counsel review, observe-ESXi-only provenance, separate spec and implementation teams |
| Fragility of VDDK-free paths: untested on 9.x, NFC can change in any ESXi release, `/folder` throttling and lock collisions | Medium | Lab-test on 8.0 U3 and 9.x each release. Avoid internal calls |
| Dependence on third-party replacements: OpenVDDK has one maintainer and is v0.x, vectura is AGPL, Cloudbase's licence is unclear | Medium | Treat them as references only and do not ship them |
| Customer-side market: Standard/Ent+ capped at 8.0 U3, vSphere 8 support ends October 2027, VVF gone in parts of EMEA, free ESXi unusable | Medium | Target 9.x first, check the licence at onboarding, fail cleanly on free hosts |
| .NET toolchain: very large WCF proxies, svcutil bugs, VI/JSON works only on vCenter | Low–Medium | Trimmed or hand-written vim25 client for about 30–50 operations |
| Lab compliance: evaluation resets and VMUG licences do not cover commercial QA | Low–Medium | TAP NFRs or a paid VVF subscription |

## Recommendations for the Phase 2 roadmap

| # | When | Action |
|---|---|---|
| 1 | Now, during Phase 1 | Register and apply to TAP, because membership is free and approval lead time is unknown. Once onboarded, ask in writing for VDDK access, the redistribution agreement text, NFRs for 8.0 U3 and VVF/VCF 9.x, and whether restoring to XCP-ng or Hyper-V counts as "backup and recovery" |
| 2 | Before signing any Broadcom agreement | Have EU/German and US counsel review the TAP Membership Agreement, the VDDK licence and the redistribution terms. Look specifically for reverse-engineering, confidentiality and scope clauses that would block a VDDK-free path |
| 3 | Phase 1 architecture | Define a hypervisor-neutral interface (changed-extent source plus random-access reader/writer). Run each hypervisor data mover as a separate worker process on a Linux x86-64 proxy, so VDDK and VDDK-free movers can be swapped |
| 4 | Phase 2 control plane | Write a thin vim25 client in C#, either trimmed and generated at build time (ship the compiled client, not the WSDL) or hand-written over `HttpClient`. Add VI/JSON optionally for vCenter 8.0 U1+. Use govmomi and pyVmomi as Apache-2.0 references. Do not bundle PowerCLI DLLs |
| 5 | Phase 2 data path, baseline | Ship VDDK-free HotAdd first: snapshot, attach with `ReconfigVM_Task`, read the CBT extents, detach, with a crash journal and a sweep for leftover attached disks. Use ExportSnapshot/ImportVApp as a full-only fallback, and `/folder` only for small config files. Use a persistent attach for block-level restore |
| 6 | Phase 2 network mode | If TAP grants VDDK, add NBDSSL as the default through `[LibraryImport]`, one worker per VDDK version, shipped under the redistribution agreement. If not, build a clean-room C# NFC reader only after counsel signs off, using separate spec and implementation teams and a provenance log for each behaviour. Never copy AGPL, LGPL or unclear-licence code |
| 7 | Lab | Start with an eval-mode nested lab on one physical host built with Lam's scripts. Move to TAP NFRs, or budget for VVF at about $2,160 a year for 16 cores after confirming with a German reseller that it is still sold there. Use vcsim in CI with a `QueryChangedDiskAreas` mock, and free ESXi only for negative tests |
| 8 | Product policy | Require a paid vSphere licence. Detect free-licensed hosts (licence check, read-only API faults) and report them clearly. Support 8.0 U3 and 9.0/9.1 |
| 9 | Sequencing | If TAP has made no progress by the time Phase 2 planning starts, consider moving Hyper-V ahead of vSphere, since Hyper-V has no access barrier |
| 10 | Ongoing | Re-check VDDK policy, TAP terms and the replacement projects at Phase 2 kickoff and again before GA. The August change came without any announcement |

## Conclusion

The question has shifted from "how do we get VDDK" to "how little can we depend on it". Before August 2026, building on VDDK was the obvious choice. Today it is a revocable, discretionary licence limited to backup only, and it sits awkwardly with a product whose natural selling point is moving VMware workloads onto XCP-ng. The cheapest insurance is a VDDK-free HotAdd path built entirely on public APIs, with VDDK added as an accelerator if Broadcom says yes, rather than the foundation. The order of steps matters legally. Decide whether you want a clean-room NFC option before you sign partner agreements, because a signed contract can waive in the US, and partly in the EU, what the law otherwise allows.

The landscape is also changing quickly in the product's favour. Within ten weeks of the cut-off, the XCP-ng vendor itself shipped a VDDK-free data path, nbdkit deprecated its VDDK plugin, and an Apache-2.0 drop-in replacement appeared. By the time Phase 2 starts, the VDDK-free approach has a fair chance of being the mainstream non-incumbent pattern rather than a workaround. That is a forecast, not an established fact, so plan for both outcomes. Meanwhile, Hyper-V's complete lack of gatekeeping makes it the lower-risk second platform if Broadcom's answer is slow.

Found in the user's environment on 2026-11-02: restoring to `\\corp.example\dfs\Shared` (a DFS link) failed on the rename. SMBLibrary 1.5.8.1 does not follow DFS links itself, and through the namespace server the new name of a rename cannot address the link target. The connector now resolves the path with a DFS referral (FSCTL_DFS_GET_REFERRALS on IPC$, up to 4 hops) and works on the target share directly; as a fallback the rename also tries the DFS forms `server\share\path` and `\server\share\path`, and if no name works, the complete temporary file is copied to its name (not atomic; noted once in the session log). The DFS referral answer is written to the session log for diagnosis. Not testable against Samba (no DFS namespace; its referral answer is STATUS_NOT_FOUND). Confirmed on 2026-11-02 in the user's environment: the DCs (10.16.1.1/.2) answer the referral for `\corp.example\dfs\Shared` with STATUS_NOT_FOUND, every rename form fails (OBJECT_PATH_NOT_FOUND, INVALID_PARAMETER), and the copy fallback restores the file; the user verified it on the link target `\\fs01.corp.example\Shared` with its original date. Bug found by the user: the fallback left its temporary file behind (fixed: deleted on close after the copy). The namespace servers are dfs01/dfs02, not the DCs: a DC answers only the root referral (`\server\share`) of a domain-based namespace, so the connector now asks for the whole name first and then for the root, then asks the namespace server for the link and connects to the link target directly (stays on the current server if a root referral lists it; loop guard). A session that needed a target fallback ends with Warning. Confirmed the same evening: DC → root referral (DFS01/-2) → DFS02 link referral → `\\fs01.corp.example\Shared`, written there with a normal rename. Short NetBIOS names (`\\corp\dfs`) do not resolve on the Linux server; the error now says to use the full DNS name.

Found while testing: `SessionEventWriter` called `Count` on its single-reader channel during shutdown, which throws `NotSupportedException` and stopped the host before the last log lines were written (e.g. "the backup service stopped" of open browsers). Fixed with `TryPeek`.

Found by `unzip`: .NET's `DeflateStream` writes nothing for empty input, which is not a valid deflate stream; the writer adds the final empty block itself.

## Findings from the hostile image tests

A corrupted inode can claim a size of several exabytes, and reading it yields zeros forever. Files larger than 16 × their volume (at least 1 TiB) are therefore reported as unsupported ("implausible size, corrupt metadata?").
